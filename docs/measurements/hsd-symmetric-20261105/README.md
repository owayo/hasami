# HSD v5と左右同一IDの4B形式の比較（2026-11-05）

**左右文脈IDが全件同じときに片方を省く方式をv6として採用した。**
3辞書の内容・候補順・同点処理・全トークンの全フィールドを保持し、完成ファイルは
0.78 / 9.31 / 10.11MB減った。混合文で解析時間の中央値の比は−2.07 / +0.19 / −0.99%、
プロセス全体のPeak Working Setは1.16 / 7.49 / 8.49MiB減った。
負荷のあるWindowsでの測定であり、一定率の高速化は結論にしない。

数量・月の専用形式は[前回の容量試作](../hsd-numeric-20261105/README.md)で削減が小さかったため採用しない。
今回も数値の読みを生成したり、存在しない数値と単位の組を候補に増やしたりしていない。
仕様は [hsd-v6.md](../../hsd-v6.md)、実装前の判定条件は [design.md](design.md)。

## 比較対象と実行環境

- 基準ソース: `e7a65059272e07087d555575b13b2ed53d1d3e28`（v5）。ユーザー指定の
  `78f63181f2f436f8dd819fee5e2ff9d422fa1b52`以降の数量・月の補正を含む。
- 試作: 同じソースを基に実験版5013とflag bit1を追加。計時した実行ファイルは
  [manifest.json](results/manifest.json)のSHA-256で固定した。
- 最終v6との差は形式番号、説明、コンテナの非公開定数名。エントリ読み出しとラティスの
  ホットパスに追加の変更はない。独立レビューでコードとハッシュを照合した。
- Windows 11 build 26300、AMD Ryzen 7 5700X（8 core / 16 logical CPU）。
  Rust 1.98.1、Python 3.13.15。両方式とも論理CPU2（affinity mask 4）に固定。
- ライブラリは`--release --locked --no-default-features --features build`でビルド。
  共通評価器 `scripts/hsd-format-eval.rs` は両方とも
  `rustc --edition=2024 -O -C lto=fat -C codegen-units=1 -D warnings`でリンクした。
- 3辞書とも計測開始時のv5を同内容の4B形式に変換して比較。
  辞書・入力・実行ファイル・変更したruntimeソース・計測スクリプトの全SHA-256を保存した。
  正式移行はこの変換器を使わず、同じ固定上流・独自入力とrepair順で再構築した。

## 入力

本文は格納しない。抽出処理は [prepare.py](prepare.py) と基準ソースの
`scripts/hsd-format-corpus.py`、内容識別子はmanifestにある。

| 入力 | 行数 | UTF-8のB数 | 内容 |
| --- | ---: | ---: | --- |
| mixed | 145,178 | 25,748,320 | 公開ニュース、基準ソースの技術文書、合成会話・ランダム文字列・境界例・数量360文 |
| short | 100,000 | 5,500,000 | 「東京都に住んでいる人々が増えている。」の反復 |
| literature | 15,424 | 8,488,992 | 青空文庫の本文482行を32回反復 |
| quantities | 360 | 11,616 | ASCII・全角・漢数字、単位・月・日・年、小数・識別子の合成例 |

ニュースは[livedoorニュースコーパスの配布元](https://www.rondhuit.com/download.html)の
`ldcc-20140209.tar.gz`、文学は[青空文庫の公開入力](https://www.aozora.gr.jp/cards/000148/files/752_ruby_2438.zip)。
文学のShift_JISを復号し、ヘッダ・底本以降・ルビ・注記を除去し、非空行をUTF-8/LFで保存した。
アーカイブのSHA-256はmanifestにある。数量はmixedにも含み、独立の全フィールド比較にも使った。
反復はタイマーの分解能を確保するためで、独立した文章数が増えたとは扱わない。

## 解析時間とメモリ

入力を1回ウォームアップした後、全行1回を計時する。辞書ごと・入力ごとに
12組の独立プロセス（AB / BA各6組）を実行し、辞書の順序も巡回させた。
コンパイル・辞書構築・検証と計測は重ねていない。
表の秒数は12標本の中央値、「中央値の比」は試作中央値/v5中央値−1、
「組の比の中央値」は各組の試作/v5−1の中央値。負数は短縮を表す。

| 入力 | 辞書 | v5 秒 | 試作 秒 | 中央値の比 | 組の比の中央値 | Peak WS削減 MiB |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| mixed | ipadic | 2.684950 | 2.629443 | −2.07% | −2.17% | 1.156 |
| mixed | neologd | 3.163862 | 3.169835 | +0.19% | +0.91% | 7.494 |
| mixed | 推奨辞書 | 3.258845 | 3.226708 | −0.99% | −0.98% | 8.494 |
| short | ipadic | 0.316780 | 0.312752 | −1.27% | −1.35% | 0.012 |
| short | neologd | 0.313348 | 0.304664 | −2.77% | −2.25% | 0.006 |
| short | 推奨辞書 | 0.315943 | 0.305062 | −3.44% | −2.53% | 0.006 |
| literature | ipadic | 0.827596 | 0.784896 | −5.16% | −4.55% | 0.980 |
| literature | neologd | 0.960754 | 0.874185 | −9.01% | −6.89% | 2.121 |
| literature | 推奨辞書 | 0.922039 | 0.971544 | **+5.37%** | −1.48% | 2.191 |

Windowsの`Instant`を主指標とする。Peak WSは`GetProcessMemoryInfo`の
`PeakWorkingSetSize`で、入力保持、runtime、ウォームアップも含むプロセス全体の値。
生データの互換キーは`rss_bytes`だが、LinuxのRSSとは呼ばない。
短文は辞書の一部しか触れないため、ファイル容量差と同じメモリ削減にはならない。

初回シリーズのwall時間のCVはmixedで3.2〜6.7%、shortで1.9〜4.1%、
literatureで6.8〜18.6%。PC全体のCPU使用率は8.23〜72.11%だった。
全標本と各方式の範囲・IQR・CVを [analysis.jsonl](results/analysis.jsonl)、
[summary.json](results/summary.json)に残す。
相対差のように正負を取る値に対するCVは解釈できないため、summary中の
`paired_*_relative_change.cv`を安定性の判断に使わない。
`GetProcessTimes`のCPU時間は約15.625ms刻みで、特にロードの差には使わない。

### 推奨辞書の文学入力の確認測定

初回の+5.37%を消さず、同じ実行ファイル・辞書・入力で別シリーズを追加した。
初回は試作が遅い組が5/12、ABとBAの組の比の中央値が+12.80% / −3.53%で、
方式ごとの中央値の比と組の比の中央値の符号も異なっていた。

追加は12組、AB/BA各6組。各プロセスで1回ウォームアップした後、8回の計時を平均した。
独立標本は方式ごと12プロセスであり、96個の独立標本ではない。
試作は12/12組で短く、組の比の中央値は**−1.42%**、AB / BA別で−1.18% / −3.26%だった。
方式別中央値は0.854363→0.817992秒（−4.26%）だが、CPU使用率15.38〜85.75%の負荷があり、
1組の−66.7%のような極端な値も残っている。一定の高速化率を示す材料にはしない。
追加の [生データ](confirmation/analysis.jsonl)・[集計](confirmation/summary.json)は初回と分離した。

容量とメモリは明確に減り、代表条件で継続する速度退行は確認しなかったため採用する。
静かな環境や別OS・CPUでの速度差まで確定したとは扱わない。

| ipadic | 616.00 | 620.35 |
| neologd | 666.60 | 664.75 |
| 推奨辞書 | 661.25 | 663.25 |

## 正式な再構築と容量

`scripts/dictionary-sources.json`を固定し、同一で変更のない独自入力、同じrepair工程を使って
旧v5と最終v6をそれぞれ上流から再構築した。既存の上流キャッシュがdirtyだったため、
その内容を変更せず、新しいcleanな取得場所を使った。両パイプラインが正常終了した。
元の計測v5と再構築v5の差はMETAのhasami_version（26.10.107→26.11.100）のみ。
再構築v5/v6はENTRIES以外の全セクションがバイト一致し、4Bから復元した全6Bエントリも一致した。

| 辞書 | v5 B | v6 B | 削減 B | 削減率 | zstd後の削減 B |
| --- | ---: | ---: | ---: | ---: | ---: |
| ipadic | 16,496,162 | 15,714,402 | 781,760 | 4.74% | 11,843 |
| neologd | 206,574,882 | 197,261,282 | 9,313,600 | 4.51% | 131,598 |
| 推奨辞書 | 220,985,250 | 210,871,586 | 10,113,664 | 4.58% | 149,166 |

zstd 1.5.7 `-19 -T1`で完成した6ファイルを圧縮し、展開した全バイトのSHA-256を元と照合した。
展開後の10.11MB減をダウンロード量の削減へ換算しない。
正式な値は [rebuilt-compression.jsonl](rebuilt-compression.jsonl)。
ビルド時間・構築時ピークメモリの統制した比較は行っていない。
writerは最終バイト列へ4Bレコードを直接追加し、4Bの補助配列は作らない。
非対称IDの辞書の性能と、実際のUniDic辞書の比較も未測定。
非対称モードの正しさは小さい構築辞書・破損fixtureで確認した。

## 回帰と利用側

- 3辞書×4入力の全トークン全フィールドを長さ付きバイナリで直接比較した。
  位置・原形・読み・発音・活用・単語コスト・既知語フラグも一致。
- 全件verify、数量・月の補正、同点時の先勝ち、辞書切替後のキャッシュを確認。
  矩形行列、左右非対称の未知語、32768以上の右IDを使う6Bフォールバック、
  幅・モード・ID・群末尾等の破損入力を回帰テストで確認した。
- rootの`make SHELL=C:/PROGRA~1/Git/bin/sh.exe ci`が成功。
  featureなし・analyzer・download・workspace/Pythonのコンパイルを含む。
  再構築した3辞書を`dict/`へ原子的に置換し、`--ignored distributed`の75テストが成功。
- v6のPython wheelを実際にビルドし、隔離venvへ入れてロードした。
  3辞書×360数量文の全フィールドをRust v6とバイト比較した。
- Kotonoha `d024124c1886eec543935157608ebc423eb803d3`を隔離した2つのcheckoutで検証。
  一時Cargo patchだけで旧v5・新v6に対応させ、実際のEngineの辞書ロードから
  NJD・アクセント句・HTSラベル・PhoneTone・韻律記号まで、1,360文×3辞書が一致した。
  v6へ差し替えたcheckoutの`make ci`も成功（Rust、CLI、Python、全feature）。
  学習モデルの再学習・実KNMによる推論比較は行っていない。トークンとAPIが等価なので、
  消費側の文法・発音処理を変更する必要はない。
- Kotonohaの恒久依存は既存リリースv26.11.100（v5）のまま。
  新形式を配布・利用するときは、v6を読む取得可能な固定revまたはリリースと辞書を一緒に更新する。
  一時的なローカル絶対パスのCargo patchは公開差分へ含めない。
- 文分割の例外語18,761件は一致。exportのコメント2行に含まれる入力パスだけを共通表記へ揃えると、
  生成ファイル全体も既存の組み込み表と一致した。語リストは正規化せず比較した。

結果は [rebuilt-validation.json](rebuilt-validation.json)、[python-validation.json](python-validation.json)、
[checks.json](checks.json)。checksのfeature別テスト数は重複するので、固有テスト数として合算しない。
古い形式を読む互換経路は追加せず、v1〜v5には再構築を案内する。
配布用のtag・Releaseの公開はこの作業では行っていない。

## 記録の再確認と再実行

```powershell
mise exec -- python docs/measurements/hsd-symmetric-20261105/audit.py
```

このコマンドは辞書・コーパスなしで、標本数、組の比、source archiveの全ハッシュ、
再構築・圧縮・Pythonの照合結果の整合性を再計算する。
`results/measured-sources.zip`は**実際の初回計測で使った**runtimeとスクリプト。
`confirmation/sources.zip`は実際の追加測定のスクリプト。
現在のrun.pyには測定後に、既存結果の上書き防止とverify→timings間の条件照合を追加した。
prepare.pyには短文の反復回数をmanifestへ明記した。凍結した実測値をこれらの変更で置き換えていない。

新しい実測では、空のTRIALに基準ソースを`v5-source`、比較ソースを`symmetric-source`として展開する。
archiveの`v5/`・`symmetric/`のファイルを対応するソースへ重ね、同じrelease条件でライブラリと共通評価器を作る。
manifestのSHAに合う元3辞書と公開アーカイブを用意してprepare.pyを実行し、run.pyで全件照合→交互測定する。
元辞書を差し替える場合は新しい試行とし、入力manifestから作り直す。異なる実行ファイルの標本を混ぜない。
confirm.pyは追加条件だけを別ディレクトリへ記録する。
正式再構築後のvalidate.py・compress.py、Pythonのpython-dump.py、Kotonohaのkotonoha-check.rsも添付した。
collect.pyは許可したJSONとソースzipだけを集め、ビルドログはハッシュとテスト結果行だけを公開する。
最終実装の識別子は [final-sources.json](final-sources.json)。辞書・本文・実行ファイル・非公開CSVは追跡しない。

独立レビューと限界は [review.md](review.md)。
最終のstopフックで再報告された同名定数の誤検出は、コンテナ側だけを
`KNOWN_FLAGS`から`KNOWN_CONTAINER_FLAGS`へ改名して回避した。
値・ビット判定・素性decoderは変えていない。改名後のHSDテスト、整形、impactは再確認した。
