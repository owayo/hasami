# 左右同一IDの4Bエントリをv5と比較する（2026-11-05）

基準コミットは `e7a65059272e07087d555575b13b2ed53d1d3e28`。
前回の容量試作から、実際のreader・writer・Analyzerの比較へ進む。
仕様の出発点は [前回の設計](../hsd-numeric-20261105/design.md) の第4案。

## 変更を限定する

- 隔離したソースで実験版5013を作る。ヘッダbit1で4B形式を選び、通常は6Bへ戻せる。
- 4Bレコードは `context_and_last u16 / cost i16`。両IDは前者の下位15bit。
  ビルド時に全通常エントリで左右が等しいことを検査する。行列自体が正方形である必要はない。
- 6B形式では従来どおり右IDを16bit保持する。未知語テンプレートは両モードとも従来のまま。
- レコードの長さ・アラインメント・素性参照数はロード時、IDと群の範囲はアクセス時にも検査する。
  ヒープ上の6B配列へ展開せず、mmap・所有バッファ・埋め込みを同じ読み手で扱う。
- 最初は値を返すEntrySliceの分岐で実装する。遅延が見つかれば外側dispatchも試すが、
  比較ソース・条件・試した順序を記録し、異なるバイナリの標本を混ぜない。
- trie・素性・行列・候補順・同点の先勝ち・Token・読み補正は変更しない。
  lookup / export / verify と未知語からの再選択も、同じエントリを読む。

## 比較条件

入力は前回と同じSHA-256のv5の3辞書。同一内容を新形式へ変換した試作品で比較する。
正式採用する場合の移行の正は、同じ固定上流とrepair工程からの再構築とする。

全フィールド比較を先に行う。混合入力は公開ニュース＋基準checkoutの技術文書＋独立に作った
会話・ランダム文字列・数量例。文学は公開の青空文庫入力を整えたものを用いる。
短文の反復は別条件にする。元データのSHA-256、抽出方法、反復回数を記録し、本文は追跡しない。

性能は同一のRust 1.98.1・release・LTO・評価器で測る。
CPU affinityは両版とも論理CPU2（mask=4）。各プロセスで入力1回をウォームアップし、1回を計時する。
12組、AB/BA各6組、辞書順を巡回する。コンパイル・変換・検証と計測を重ねない。
WindowsのInstantを主指標とし、GetProcessTimesの粗いCPU時計は補助値として残す。
PeakWorkingSetSizeは入力・runtime・ウォームアップを含むプロセス全体の値。
PC全体CPU使用率も保存する。cold cacheの計測とは呼ばない。

ロード＋固定短文1回は、各辞書・方式で12個の新しいプロセスを別に測る。
OSページキャッシュは温まった状態で、プロセス起動時間は内部時計に含まれない。

## 採否

全トークンの全フィールドと候補順の保持、安全性の検査が必須。
代表入力で再現する速度の退行を容量だけで覆い隠さない。
2%以上の退行が複数の代表条件で安定して現れる場合は、分岐等の原因を調べて再試作するかv5を採る。
中央値の比だけでなく、組の比・範囲・順序別の値とメモリを確認する。
僅差が負荷の揺れを超えていない場合、速度向上を主張せず容量・メモリ・複雑さから判断する。

採用する場合は正式版をv6とし、旧版の拒否・再構築案内、全feature・FFI/Python、
配布辞書の再構築と検証、Kotonohaの互換性まで確認する。
見送る場合も試作パッチ・全測定値・理由を残し、本番v5を維持する。
