# 数量語と文脈IDの格納を見直す設計（2026-11-05）

基準は `78f63181f2f436f8dd819fee5e2ff9d422fa1b52` 以降の変更を含む
`3b95cde736cc618d2e904b5f79deb138434b69c8`。現行形式は v5。
今回は格納の試作と設計の比較であり、本番の reader / writer / 解析処理は変更しない。
最終の数値・入力の識別子・再現手順は [README.md](README.md) と `summary.json` に残す。

## 最近の変更が設計へ与える条件

指定区間では `numeric` と数量・文脈の補正が増えた。特に次を失ってはいけない。

- `4fd1f2e`：空白のない ASCII 暦月。`3月` の読みを補っても、人名・識別子・独自の読みは保護する。
- `f9422bf`：月直後の暦日の `1日` は「ツイタチ」、期間は「イチニチ」。数値と日だけでは判定できない。
- `53b3e34` / `1c278a2`：月日へ続く全角年と、年の末尾4の読み。
- `51a3735` / `2344225`：既知語を含む負小数、符号と数値本体の境界。
- `1babc1c` / `1fe1f2a` / `4b24e7e`：複合単位・指数・単位全体の境界と読み。
- `fe066f3`：距離と時間が続く表記の `m`。単位の綴りだけでは意味を決められない。
- `ea10d1f`：辞書の全キー列挙で借用の緩衝を使う。オンディスク形式の変更ではない。

したがって「数値×単位」の直積を無条件に候補へ加えたり、辞書の一語を
「数詞トークン＋助数詞トークン」に置き換えたりする案は、形式変更だけではない。
既知語判定、候補順、同点、単語コスト、原形・品詞、トークンの境界まで変わり得る。
数値・単位・月の読み表は現在 Rust コードにあり、その表を HSD に移すだけでは
既存 HSD の削減にはならない。規則の共有化と辞書の格納圧縮は別に評価する。

## 試作する表現

### 1. 検索キーの数値部と後続部を共有（実験版5011）

入力キーから符号付きの数字列、漢数字列、小数点・桁区切りを含む最大の先頭部分を分ける。
この分解は文字列の格納用であり、妥当な数値や数量であると認定する規則ではない。
後続部は計測器に明記した集合との完全一致で選ぶ。「月だけ」も別に測る。
先頭が数値でない数量、先頭のラベル、すべての SI 単位表記などを網羅する調査ではない。

一般 trie から選択したキーだけを外して再構築し、次の追加セクション19を作る。

1. 接頭部数・後続部数・実在する組の数を u32 LE で記録する。
2. 接頭部と後続部は、それぞれ `(個数+1)×u32` のオフセットと UTF-8 本体で持つ。
3. 接頭部ごとの行の開始を `(接頭部数+1)×u32` で持つ。
4. 各行に `後続部ID u32 / 元のエントリ群ID u32` を後続部ID順に置く。

実在する組だけを持つ。接頭部IDを u16 へ狭める前提は置かない。
元の ENTRIES / FEATURE_OFFSETS / FEATURES と候補順はそのままにする。
一般 trie の全残存キーの完全一致検索と、追加表から復元した全キー・群IDを直接照合する。
新しい表を本番の共通接頭辞検索へ統合した reader は未実装。
入力の途中で終わる数値接頭部を含め、すべての元候補を元と同じ順に返す必要がある。

### 2. 数量語の読み・発音の語尾と前半を共有（実験版5012）

trie と ENTRIES は変えない。選択した数量形の素性のうち、原形が表層形と等しく、
読み・明示発音が既存のカタカナ詰めであるものを対象にする。
`(後続表記, 文法ID, flags)` ごとに5素性以上ある場合、読み・発音それぞれの
共通のバイト末尾（最大12B）を取る。音便を推定したり、新しい読みを生成したりしない。
同じ素性に複数の分解があれば、共有末尾の合計が長いものを選ぶ。
ID順は固定のバイト順で決め、ハッシュ表の走査順に依存させない。

- 通常レコードは v5 のまま。共有レコードは flags の bit4 を立て、
  `文法ID varint / flags / テンプレートID varint / 読み前半ID varint / [発音前半ID varint]`。
- セクション19は前半のバイト列プール。`count u32 / offsets u32×(count+1) / bytes`。
- セクション20は末尾の組。同じプール形式で、各レコードに
  `読み末尾長 varint / bytes / 発音末尾長 varint / bytes`。
- 読み・発音の符号化と省略の意味は元の flags で決まる。復元は前半と末尾のバイト列の連結だけ。
- 最終 FEATURES の順序を保ち、全エントリの u32 素性オフセットを書き換える。

固有素性の全件を v5 のバイト列へ復元して直接比較し、全エントリの素性参照も照合する。
HSD の完成ファイルと `.zst` を実際に作る。ただし Analyzer が読む実装は作らない。
この試作はプールの費用が回収できない素性も含むため、最適圧縮の上限を示すものではない。

### 3. 文脈IDの組を共有（実験版5009）

各 ENTRIES の `left, right` の組を出現順に共有する。
レコードを `pair_id_and_last u16 / cost i16` の4Bとし、追加セクション19に
`left u16 / right u16` の組を置く。組IDは15bit、MSBは従来の群の末尾フラグ。
試作は32,768組を超える入力を拒否する。全 ENTRIES を元の6B列へ復元して直接比較する。
汎用的だが、Viterbi で文脈IDを読むたびに表の参照が必要になる。

### 4. 左右が同じ場合に一方を省略（実験版5010、次の実装候補）

今回の3辞書では全通常エントリの `left_id == right_id` だった。
この性質をビルド時に確認できる辞書に限り、
`context_and_last u16 / cost i16` の4Bにする。両文脈IDは `context_and_last & 0x7fff`。
通常エントリの全件を元の6B列へ復元して直接比較する。
追加の表・参照は要らず、左IDと右IDの値、群の末尾、コスト、論理エントリ番号は保つ。
今回の試作では本番の型・reader を変えず、容量の完成ファイルだけを作る。

正式に試作 reader を作る場合の仕様は次のとおり。

- コンテナは現行64Bヘッダ・24Bセクション表・64B境界・LEを保つ。正式採用時は v6 にする。
  現在の実験番号5009〜5012を正式版として配布しない。
- flags bit0（支配エントリ除去）は維持。v6 の bit1 を対称エントリ形式とし、未知ビットは拒否。
- bit1 は「すべての通常エントリで左右が同じ」というビルド時の証明に基づいて選ぶ。
  辞書名・IPAdic 固有IDへ依存しない。一つでも異なる場合は従来の6B形式を使う。
- エントリ領域はモードに応じて4B / 6Bで割り切れること、論理件数が素性参照数と等しいことを検査する。
  4B版は両方の行列次元に対して同じIDが範囲内であることを検査する。
- `#[repr(C)]` の4B構造体と `bytemuck::try_cast_slice` を使う。独自の unchecked 参照を増やさない。
  ヘッダ計算の checked arithmetic、実ポインタの整列、mmap の更新手順は v5 を保つ。
- trie の文字写像・配置・ビット幅・TAIL・群IDの上限は変更しない。
  FEATURES の文法共有・文字列符号化とオフセットの4GiB上限、行列の向きも変更しない。
- 未知語テンプレートは従来のまま。中間辞書と最終辞書、支配エントリ除去、merge / repair の制約も維持。
- モード選択をホットループの外へ出せる構造で試作する。コード生成と性能を実測するまで
  分岐の除去や解析の高速化を達成したとはしない。
- Token の所有形、借用型、Arc キャッシュ、Viterbi 集約、ID再付番は対象外。
  FFI / Python は同じ Dictionary を通す。feature なしの文分割を巻き込まない。
- 壊れたモード、長さ、ID、群末尾、素性参照と、非対称の独自辞書へのフォールバックをテストする。

## 規則から数量候補を作る案の扱い

さらに数値列を FST 等で認識し、助数詞クラス・暦月クラスから辞書候補を復元することは考えられる。
ただし、規則だけの表現が既存辞書と等価だと結論する材料は今回ない。

- `数値の表記集合 / 実在する後続部 / 各候補の順序と左右ID・コスト / 文法 / 読みの例外` を保持する必要がある。
  期間の月、暦月、月の付く名前などの意味を、表層の末尾だけで決めない。
- 数値を連結した一語のコストは、数詞と単位のコストの和から自動的には求まらない。
  暦月だけでも今回の大きい2辞書では44エントリに43種類のコストがある。
- 読み生成と辞書候補の生成は異なる。最近の保護規則は、選択された候補の独自素性・識別子なども見る。
  既存の解析後補正を、そのままラティスの候補生成へ移すことはしない。
- 無限の数値を認識する規則は、有限の現行辞書に存在しない候補を増やす。
  「同じ内容の形式変更」と「数量解析の機能追加」を分けて評価する。

今回はこの案を実装していない。格納専用の共有表・語尾共有の結果を、その案の容量や速度の測定値へ転用しない。

## 採用へ進むための条件

前回レビューの5項目に対し、今回は3辞書の容量試作、表現・幅の記述、
中間/最終とIDの保持、共有文字列の試作を実施する。
ロード/アクセス時の破損検査の実装とテスト、Analyzer による全フィールドの回帰比較、
初回・混合/文学/短文の速度とメモリ、構築時間とピークメモリはまだ満たしていない。
Viterbi 集約は既存の不採用記録を維持し、組み合わせない。

したがって容量だけで正式な v6 は採用しない。次に実装するなら表現4を単独で比較する。
同じ辞書内容と同じ入力で全トークンの全フィールド・同点を確認し、
AB/BA順の性能比較と全feature・FFI/Pythonの検査を通してから決める。
正式移行の正は固定した上流と同じ repair 工程からの再構築であり、試作変換器ではない。
今回の結果は `docs/hsd-format.md` に追記し、再構築と配布は行わない。
