# TAIL の u16 文字符号を評価する設計（2026-10-05）

基準は `4de1d02` の v5、入力は公開リリース `v26.9.107` の3辞書。
速度と初回メモリを優先し、第9.3節で容量のみ試算した TAIL 文字符号案を単独で試す。
製品への採用は決めず、隔離したソース・実験版5007で評価する。

## バイト配置

- コンテナ・18セクション・64B整列・ノード種別・DA配置・候補順はv5と同じ。
- TAIL は `value: u32 LE`、`文字数: u32 LEB128（最大5B、1以上）`、
  `文字数 × u16 LE の文字符号`。符号は既存の CHAR_BLOCKS / CHAR_TABLES の1..=N。
- レコード内の追加整列はしない。読み出しは `u16::from_le_bytes` を使い、
  非整列の型付き参照やunsafeを追加しない。
- TAILノードの下位30bitは引き続きバイトオフセット。TAIL列は1GiB未満、
  値は2^30未満。UTF-8の逆変換に必要な文字写像は既存の表を使う。
- 変換対象はTRIE_TAILSとTRIE_NODES内のTAILオフセットだけ。
  他の16セクションはバイト一致を検査する。素性・支配エントリ・文脈IDは変更しない。

## 読み出しと検査

共通接頭辞検索のINTERNAL遷移は現行のまま。TAIL到達時に残る文字イテレータと
u16符号列を比べ、入力側のUTF-8バイト長を足して終了位置を求める。
事前符号版も通常版も同じ本体を使う。文字列・借用型を広げず、トークン生成やキャッシュも変えない。

TAILの値、varint、長さ×2のchecked arithmetic、範囲、全符号の0・N超過をアクセス時に検査する。
全件検証・キー列挙では既存の文字写像の全単射検査も維持し、符号からUTF-8のキーを復元する。
ロード時に全TAILを読む処理は追加しない。切り詰め・varint・符号の破損を小さい辞書で確認する。
入力が短い場合や先頭で不一致になる場合にも全TAIL符号の検査を省略しない。
隔離ソースの `Placer::place_last_key` も同じu16表現へ変え、小辞書を構築する検査に使う。
これは正式writerの評価や上流からの再構築ではない。
メモリ更新は今回の試作ファイルへの新規書き出しだけで、元の配布辞書を置き換えない。

## 測定と採否

入力辞書・コード・測定器・コーパスのSHA-256を保存する。既存の固定配布品と
混合143,874行、固定短文100,000回、文学48,200行の入力をハッシュ確認して再利用する。
3辞書すべてで全トークン全フィールドを直接比較し、元の全TAILを符号から復元して一致を確かめる。

Windows、同一toolchainとrelease設定。CPU affinityを両方式でそろえ、AB/BAと辞書順巡回、
ウォームアップ後の解析時間・プロセス全体のPeakWorkingSetSize・負荷を全標本保存する。
`Instant` の高精度な経過時間を主指標とし、前回15.625ms刻みだったCPU時計は補助値とする。
ロード＋1文の単発プロセスも別に測り、31回再構築のピーク値を初回メモリと取り違えない。
OSキャッシュは温まった条件。cold cacheの費用や他OSへの普遍的改善は主張しない。

速度・初回メモリに再現する利点がなければ見送る。速度差が揺れるなら未確定とする。
小容量だけで形式を上げない。正式writer・上流からの再構築・構築時間/ピークメモリ・
配布圧縮・FFI/Python・UniDic・32bitの未検証を区別する。

独立したCodexエージェントに設計と結果を確認させる。
指定された `ai-second-opinion` スキルはこの環境のスキル一覧・ローカルディレクトリに存在しないため、
外部CLIレビューの代わりにこの実行環境の別エージェントを用いる。
外部CLIレビューを完了した扱いにはしない。
