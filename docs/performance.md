# 解析の高速化の記録

形態素解析（`Analyzer::tokenize`）と `hasami tokenize` を速くしたとき（2026-09）に、測ったこと・試したこと・
決めたこと・見送ったことをまとめる。次に速度を見直すときの出発点にする。辞書形式そのものの検討は
[hsd-format.md](hsd-format.md) にある。

- 数値は Apple M2（P コア 4 + E コア 4）、`cargo build --release`（lto = "fat"）で取った
- コーパスは livedoor ニュースコーパス（ldcc-20140209）の本文 132,876 行・24.3MB（各記事の 4 行目以降の空でない行）。
  解析だけを測るときは、行ごとに `Analyzer::try_tokenize` を呼んで出力を作らない（`hasami bench --file` と同じ）
- 計測したマシンはほかの作業で負荷が高く、E コアに回されると値が倍近く揺れる。解析だけの計測はスレッドの QoS を
  USER_INTERACTIVE にして P コアに寄せ、変更前と変更後を交互に 3〜5 回ずつ走らせて最小値で比べた

## 2. 採用したこと

codex に設計を相談し（ai-second-opinion）、効果を分けて測りながら入れた。解析結果は、コーパスと合成の
入力 4 万行（記号・BMP 外・制御文字・長い英数字の並び・句点の無い長文など）、稀なブロックの文字（結合文字・異体字
セレクタ・ZWJ の絵文字・私用領域など）を混ぜた乱数の入力 1.5 万行で、3 辞書とも全トークンの全フィールドが変更前と
完全に一致することを確かめた。`hasami tokenize` の出力（MeCab 形式・分かち書き・JSON、`-j 1` と並列）も変更前と一致する。
文分割の走査は、`chunk_ends` と `split`（改行の扱いの各設定、利用者の例外語、`split_with_breaks`）の結果が、全 Unicode
スカラー値と短い文字列の全組み合わせを含む数千万件の入力で変更前と一致することを確かめた。

| 変更 | 内容 | 変更前比（ipadic / 推奨辞書） |
| --- | --- | ---: |
| 文字ごとの前計算 | チャンクの文字ごとに、バイト位置・trie の符号・文字種・同じ文字種が続く長さを 1 回だけ求める（`ChunkChars`）。trie は符号の列を辿る（`Trie::common_prefix_search_codes`）。未知語の長さは続く長さから O(1) で決める（英数字の長い並びで 2 乗にならない）。位置はバイトでなく文字の番号 | -19% / -14% |
| 文字種の表 | `classify_char` と同じ結果を返す BMP の 64K の表を辞書ごとに持つ（BMP 外は従来どおり） | （上に含む） |
| 挿入時の Viterbi | 開始位置の昇順にノードを作るので、位置 i では i で終わるノードが揃っている。ノードを作るときに最良の前ノードを決める。i で終わるノードが無い位置は辞書引きもしない | -31% / -27% |
| 終了位置ごとの AoS | `ends[pos]: Vec<Node>`（累積コスト・エントリ・前ノードの番号・開始位置・right_id・単語コスト、24 バイト）。前ノードを連続した領域で走査する。トレースバックは (位置, 番号) を辿る | 段階 2 比 -4% |
| 出力へ直接積む・列の使い回し・読み補正 | チャンクごとの `Vec<Token>` と extend をやめる。終了位置ごとの列は 1,024 位置まで容量ごと残す（短い入力が来ても捨てない）。読み補正は「数」「一節」のときだけ前後のトークンを調べる | -44% / -41% |
| 品詞・活用・空文字列の `Arc` を解析器ごとに | 下の 2.1 | 並列で効く |
| 前分割の走査 | `Splitter::scan` は、かなの先頭バイト 0xE3 が候補に入るので 1 字ごとに止まっていた。8 バイトの語の演算で候補の先頭をまとめて求める。区切りの列は解析器が使い回す（`chunk_ends_into`） | `chunk_ends` 66→42ms、`split` 77→54ms |

### 2.1 共有する `Arc` の参照カウントの取り合い

`Token` の品詞・活用型・活用形は辞書の表の `Arc<str>`、空文字列は `static` の `Arc<str>` を複製していた。
複数のスレッドで解析器を並べると、全スレッドがトークンごとに同じ参照カウントを更新するので、キャッシュラインを
取り合って並列に解析しても速くならなかった（`hasami tokenize -j`、分かち書き、ipadic）。

| スレッド数 | 1 | 2 | 4 | 8 |
| --- | ---: | ---: | ---: | ---: |
| 辞書の `Arc` を複製（変更前） | 1.13s | 0.73s | 0.71s | 0.82s |
| 解析器ごとの写し（`TokenBuilder`） | 1.16s | 0.66s | 0.42s | 0.39s |

解析器ごとに同じ内容の `Arc` を作ってトークンに入れる（初めて使う品詞だけ作る。品詞は 69、活用型 58、活用形 28）。
`Token` の型は変えていない。

### 2.2 CLI（`hasami tokenize`）

- 標準出力を `BufWriter` にした。Rust の標準出力は行バッファなので、入力 1 行ごとに書き込みの
  システムコールが出ていた。読み込みが待つ前には出力を書き出すので、行を送って結果を待つ使い方も詰まらない
- 標準入力は 256KB ずつ読み、完結した行のブロックを 16KB ほどのまとまりに分けて、`-j`（既定は CPU の数）の
  スレッドが空いた順に取って解析する。P コアと E コアのように速さの違うコアが混ざっても遅いスレッドを待たない。
  出力は入力の順。読み込みの単位は 1MB より 256KB の方が速く、最大 RSS も小さかった
- JSON は serde_json の `Value` を作らずに書く（キーの並びは従来と同じアルファベット順、文字列のエスケープは serde_json）

## 3. 試して見送ったこと

| 試したこと | 結果 |
| --- | --- |
| trie の探索だけを先にまとめて行う（位置ごとの探索は独立なので、メモリ待ちを重ねられる見込み） | 探索は ipadic 0.17s・推奨辞書 0.36s（1 パス）と分かったが、全体は速くならなかった |
| Viterbi の集約（(位置, left_id) のメモ、right_id ごとの前ノードの集約） | 内側の反復は 13〜27% 減るが、反復は分岐なしの 11 命令で、全体の約 12% しか占めない。ノード・前ノードごとに表を引く費用の方が大きい |
| 支配される前ノードを追加時に捨てる（同じ right_id で累積コストが大きいもの） | 追加のたびに同じ位置の列を走査するので、省ける反復と同じだけ費用がかかる |
| トークンキャッシュを大きくする | 命中率は 1,024 スロットで 71〜74%、4,096 で 83〜86%、65,536 で 96〜98%。4,096 でも 1〜3% しか速くならず、解析器ごとに約 0.4MB 増える。命中しても `Arc` 7 本の複製（原子的な加算）が残るため |
| 累積コストを i32 にする | チャンクの長さに上限が無く、桁あふれで最良パスが変わりうる（codex と一致） |
| unsafe で境界検査を外す | Viterbi の内側の境界検査は予測の当たる分岐 1 つで、効果が小さい |

`Token` の文字列を `Arc<str>` 7 本で持つ限り、トークンの生成と破棄で原子的な加算・減算が 14 回ずつ要る
（トークン生成と破棄で全体の約 20%）。型を変えるのは noslop などの利用者に影響するので見送った。

## 4. 最終の計測

解析だけ（1 パス、変更前と交互に 5 回ずつ走らせた最小値）:

| 辞書 | 変更前 | 変更後 | 差 |
| --- | ---: | ---: | ---: |
| ipadic | 1.84s | 1.00s | -46% |
| ipadic-neologd | 2.23s | 1.29s | -42% |
| ipadic-neologd-sudachi | 2.29s | 1.34s | -42% |

`hasami tokenize`（標準入力から全行、3 回の最小値）:

| | MeCab 形式 | 分かち書き | JSON |
| --- | ---: | ---: | ---: |
| 変更前（ipadic） | 2.33s | 2.23s | 5.61s |
| 変更後 `-j 1`（ipadic） | 1.24s | 1.13s | 1.70s |
| 変更後 既定（8 スレッド、ipadic） | 0.43s | 0.39s | 0.53s |
| 変更前（推奨辞書） | 2.80s | | |
| 変更後 `-j 1` / 既定（推奨辞書） | 1.62s / 0.49s | | |
| 参考: MeCab 0.996（`mecab -b 1000000`、ipadic） | 3.09s | | |

この後、未知語の候補の作り方を MeCab と同じにして配布辞書を作り直した（解析結果は変わる。[hsd-format.md](hsd-format.md) の 7 章）。
作り直した辞書でも解析の時間は同じ（ipadic 1.00s、ipadic-neologd 1.29s、ipadic-neologd-sudachi 1.33s）。
続けて足したカタカナの並びの規則（README の「未知語」）は、3 字以上のカタカナの並び（コーパスの文字の 16.7%）に
入ったときに、並びの各位置の辞書引きを先に済ませる（`RunCover`）。引いた結果を並びの中の位置でそのまま使い、
同じ位置を 2 度引かないので、解析の時間は変わらない（2 度引いた版は CPU 時間で 6〜11% 遅かった）。

辞書のロードから 1 文の解析まで（初回、20 回の中央値）は変更前と同じ 0.4〜0.7ms。文字種の表は、Unicode のブロックに
よる判定を範囲の表にして塗るだけにしたので、ロードは遅くならない（65,536 字をそれぞれ判定すると約 0.5ms かかった）。
